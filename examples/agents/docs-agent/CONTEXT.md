Domain facts I need on every turn. This file changes when the domain changes —

## The project I document

`example-service` is a small HTTP service that stores records and exposes them
for download. The office maintains its **documentation and review**; it does not
own the source. Three endpoints matter for documentation purposes:

- `GET /records` — paginated listing.
- `GET /records/{id}` — one record.
- `GET /export` — a bulk download of all records, the endpoint most questions
  are about.

## Where documentation lives

| Path | What it is | Audience |
| --- | --- | --- |
| `docs/README.md` | What the service is, and how to run it locally | Someone who has just cloned it |
| `docs/api/` | One page per endpoint, generated by hand | Someone integrating against it |
| `docs/guides/` | Task-shaped pages: "export everything", "paginate safely" | Someone with a goal, not a question |
| `CHANGELOG.md` | Reverse-chronological, one entry per released version | Someone deciding whether to upgrade |

The split is deliberate: `docs/api/` answers *what does this parameter do*, and
`docs/guides/` answers *how do I accomplish X*. A page that tries to do both does
neither, and the guides are where that pressure shows up first.

## Conventions that are not negotiable

- **Every endpoint page has the same five sections**, in this order: what it
  does, parameters, response shape, errors, an example that was run.
- **Examples use `curl`**, one flag per line, so they can be copied into a
  terminal and read in a diff.
- **Placeholders are `<angle-bracketed>`** and obviously fake. Hosts in examples
  are `example.invalid`, which is reserved and cannot resolve.
- **Dates in examples are ISO 8601 with an explicit offset.** The date format is
  the single most common source of integration bugs against `/export`, so
  examples never show a bare local date.
- **British or American spelling — pick one per page and stay consistent.** The
  existing pages are American; new pages match their neighbours.

## What I do not touch

- Any file outside `docs/` and `CHANGELOG.md`.
- Source files, tests, and CI configuration — including comments in them.
- The service's own `--help` output, which is generated from source.

## Standing gotchas

- **`/export` streams**, so a naive example that pipes it into a variable will
  appear to hang on a large dataset. Every example for it writes to a file.
- **The changelog is read by people deciding whether to upgrade**, so an entry
  that says "various fixes" is worse than no entry. Each one names what changed
  and what a reader must do about it, if anything.
- The API pages were written before pagination existed, so any page that predates
  it may describe unbounded listing. Check the parameter list against the current
  interface rather than trusting the prose.
